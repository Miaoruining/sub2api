# 延迟优化与验收边界

## 当前证据

2026-09-10 发布分段诊断后，只读核对真实业务请求，未发送付费模型测试。近期 CallAI 两笔样本分别为：

| 样本 | 请求发送完成 | 收到首个响应字节 | 结果 |
| --- | ---: | ---: | --- |
| A | 19 毫秒 | 36,965 毫秒 | HTTP 200 |
| B | 85 毫秒 | 125,108 毫秒 | HTTP 524 |

时间均从本站上游调用开始计算，两笔事件有序且连接、写入事件各一次。A 复用连接，B 在 82 毫秒取得连接。它们的主要等待发生在发送完成之后；不能据此进一步区分供应商网关排队、模型处理和响应回程，也不能把供应商后台显示的生成耗时直接当作同一测量口径。

历史另有大请求写入阶段达数十秒的样本，不能用上述两笔否定那类异常。需要继续核对同一时段主机内存、网络及 HTTP 流控。诊断只记录慢成功请求和错误，因此这些日志不能直接用于计算全站成功率或无偏的首字分位数。

另一个供应商的 OpenAI Responses 请求出现 503 和五轮同账号退避，等待分别为 0.5、1、2、4、8 秒，累计 15.5 秒，不包括每次上游处理时间。这是现有显式五次重试配置；需要评估末尾重试挽回的成功请求后才能降低预算。不可把下述 Anthropic 修复声称为该 OpenAI 路径的修复。

## 本次代码改进

通用 Anthropic 转发与 Anthropic API Key 透传在特定配置组合下，同时存在 Service 内层五次尝试和 Handler 外层池模式重试。外层每次重新调用 Service 都会重置内层预算。

当池账号的状态码明确由外层同账号重试接管，且该路径确实支持返回 failover 错误时，只保留外层为重试所有者。管理员配置的重试次数继续决定预算，避免乘法放大。非池账号、未交给池模式的状态码及请求参数修复保留既有行为。

此修复主要影响启用了自定义错误码、并触发内外两层重试的 Anthropic 池账号。不能宣称所有正常请求都会提速，更不能宣称已解决三家 OpenAI 供应商的全部慢请求。

本地验证通过：Service 定向测试覆盖真实转发调用计数、池账号 429/503、非池五次尝试、自定义 400/404 和取消退避；Handler 定向回归覆盖外层重试预算、取消和已写出语义内容后的 failover 保护。两组分别运行 10.486 秒和 7.855 秒，`git diff --check` 通过。

## 下一步上线与验收

- 本轮代码先完成本地验证；生产只读排查，不重启、不调整模型、计费或账号重试配置。
- 要缩短发送完成后的等待，需取得供应商可用的备用入口或低延迟线路，在同模型、推理强度、输入与缓存规模下对照验证；没有等价替代线路时，不截断长请求来制造更低耗时。
- 用户补充的 `wawazz.xyz`、`sub.callai.one`、`api.novaris.com.cn` 与当前生产入口一致，不能当作新线路进行切换。
- 首字和总耗时必须与成功率、超时率一起验收，并区分内部重试次数和用户请求数。供应商请求 ID 可用时优先用它对齐，不仅按时间猜测。
- 下一次发布保留现有内存软预算和回退镜像。4 GB 主机曾在双实例期间发生资源不足，必须先验证容量，不能仅凭健康接口通过就并行启动两份生产负载。
