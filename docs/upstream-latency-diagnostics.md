# 上游慢请求分段诊断

用户使用记录与供应商使用记录的计时起点可能不同。比较时先用上游请求编号关联；没有编号时，用时间、模型及输入、输出、缓存 Token 匹配，并保留匹配不确定性。供应商展示的总输入可能包含缓存，不能直接与本站未缓存输入列比较。

## 需要区分的时间

- HTTP 入站整体耗时：可能包含读取客户端请求体、认证、选路、并发等待、失败切换及最终响应。
- 使用记录耗时：由具体转发路径的计时起点决定。一次成功转发的记录不代表此前所有失败尝试和前置等待。
- 出站诊断：围绕一次 HTTP 调用记录连接、请求发送、上游响应及响应体消费的时间。不是客户端实际收到或渲染文字的时间。
- 首字：本站可能等待语义事件或有效内容，而供应商可能使用不同规则。首字差距与总耗时差距需同时比较。

## 采集方式

普通 HTTP 上游调用通过 `net/http/httptrace` 记录有界事件时间线，包含获取连接、DNS、TCP、TLS、请求发送完成和首次响应字节。记录连接复用、请求内容长度等数值，配合响应头返回和首次响应体读取的时间，区分短响应头、长内容等待的情况。

诊断不能预读或缓存响应体，不能调整请求重试、连接限制、响应刷写或计费规则。调用达到 5 秒或发生错误时，输出一条 `http_upstream_trace` 摘要。成功调用在响应体关闭时输出，出站调用失败时立即输出；响应体消费时间包含本地处理及下游背压，不能直接称为上游生成时间。

摘要中的 `client_acquire_ms`、`response_headers_ms`、`got_first_response_byte_ms`、`first_body_read_ms` 与 `total_ms` 都是相对于该次出站调用开始的时间。`events` 保存至多 64 个连接/发送事件，超出时标记 `events_truncated`；事件中的 `at_ms` 使用相同起点。`first_body_read_ms` 是调用方首次读到非空响应体的时间，并不代表数据实际到达网卡的时间。

`client_acquire_ms` 包含出站目标校验及客户端获取，不能直接称为连接池排队。TLS 指纹专用传输路径未增加这套诊断；普通 API Key 上游和转发到 Chat Completions 的路径均经普通 `Do` 调用采集。

不写入请求/响应正文、认证头、Cookie、完整 URL、客户端地址或错误原文。直接上游响应编号只接受经过验证的 UUID；不把任意响应头内容直接写入日志。

## 阅读方法

1. 先用本站请求编号关联一次请求的使用记录和出站诊断；外层失败切换可能产生多条出站诊断。
2. 获取连接之前的时间需结合客户端获取、DNS、TCP 和 TLS 事件判断，不能全部称为连接池排队。
3. 连接获取到请求发送完成之间的时间可用于定位上传等待；HTTP/2 多路复用、重连和重传仍需结合事件时间线分析。
4. 请求发送完成到上游首次响应之间，包含网络传播和上游处理或排队。仅凭本站日志无法继续拆解供应商内部耗时。
5. 若响应头很早到达、有效内容很晚出现，继续对照首次响应体读取与使用记录首字；原始响应体的首字节不等于首个有效 Token。
6. 多次连接尝试或缺失回调时，不盲目相减。缺失事件表示未观测到，不表示该阶段耗时为零。

## 生产核验边界

优先采集真实业务流量；基础模型列表接口的快速响应，只证明该短请求链路正常，不能代替模型生成请求的测试。并发配置不是实际并发；成功使用记录重建的并发不包含失败或尚未完成的请求。TCP 累计重传不是某笔请求的重传，应使用同一时间段的增量及连接对应关系。

部署后需核验至少一笔慢请求能关联到摘要、流式响应和用量记录保持正常。回滚使用部署前的镜像版本；诊断不需要数据库迁移。不要通过改小耗时展示值来掩盖实际等待。

本地验证命令（在 `backend` 目录运行）：

```sh
go test -race ./internal/repository -run 'TestHTTPUpstream|TestDecompress|TestTracked' -count=1
```

测试包含回调组合与竞态、有界事件、缺失时间点、快速响应头后的慢流、敏感信息排除、原始读取/关闭错误保留，以及真实本地 HTTP 流式服务不被提前读取的检查。
