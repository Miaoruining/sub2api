# 订阅补充额度包

基础套餐和补充包使用不同商品类型。基础套餐建立订阅周期；补充包只增加下单时绑定周期的可消费额度，不重置用量、不延长到期时间。补充包每笔订单独立记账，重复支付回调不会重复发放。

## 商品配置

- 基础套餐设置 `plan_kind=base`，30 天，不允许有效期内续订；额度来自绑定分组的月限额。
- 补充包设置 `plan_kind=topup` 和 `quota_usd`，绑定对应订阅分组。只允许有该组有效订阅的用户购买，购买次数不限。
- 购买确认页展示本期到期时间；补充包的订单快照保存订阅 ID、周期起点和新增额度。
- 付款回调到达时原周期已结束或变更，订单进入 `REFUND_REQUESTED` 等待处理，不向新周期发放。
- 两笔禁止续订的基础订单同时付款时，通过数据库事务锁串行分配；已有有效订阅的另一订单进入退款请求，不延长为 60 天。

## 消费与退款

当前周期基础限额加已付补充额度共同构成可消费限额。实际消费超过基础限额后，按顺序归属到补充包；归属不明确的额度仍保留已付权益，但不能按未消费包自动退款。旧周期补充额度不结转到新周期。

未消费补充包只支持全额退款，先撤销权益并失效缓存。网关退款失败时恢复权益；恢复失败或网关已退款但本地终态保存失败时，保留明确的人工对账状态。已消费包的强制退款属于人工补偿，不代表自动退回未用余额。

请求在旧周期开始、新周期建立后才结束时，不扣新周期或充值余额。`subscription_billing_failures` 保存请求、周期及费用命令，供人工对账；重复失败记录按请求 ID 和 API Key ID 去重。此记录不会自动补扣或重放。

现有网关在请求完成后结算，尚无整笔请求费用的并发预留机制，因此单次请求或并发请求可能产生超额消费。套餐额度不是严格的模型成本上限。

## 发布和回退

迁移 `246_subscription_quota_packs.sql` 只做前向扩展。旧基础商品保留历史续订行为；部署后需显式关闭本次三档基础商品的有效期内续订，再开放销售。

先备份数据库，按现有候选实例、切流、排空流程部署。所有旧进程退出后再上架补充包。若回退到不支持补充包的旧应用，必须先停止补充包销售并检查待付订单与回调，不能让旧版本把补充包当充值处理；不要恢复旧数据库覆盖新订单和消费。

## 模型广场

共享渠道按各分组模型白名单过滤。一个模型的平价和多个分时倍率合并为一行展示，保留上下文阶梯、缓存价格和完整时段提示。国产分组与开发者订阅渠道分别配置，避免国产分组混入 GPT。
