# 拼单账号动态均分额度设计

状态：两种可选模式已于 2026-09-10 发布生产，应用提交 `11adc378e`；真实 OAuth 账号的采样验证仍需在动态观察模式进行。发布过程见 [生产发布记录](release-modelport-20260910-pool-dynamic.md)。

## 目标与数据边界

以账号实际上游额度窗口为容量依据，以成员累计消耗为公平依据。保留现有官方 API Standard `$` 使用记录，但不把固定 `$` 预算视为订阅的真实总容量。

旧 `credits` 模式继续使用 `backend/internal/repository/pool_credit_repo.go` 的固定 `$` 规则。新模式通过 `pool_dynamic_repo.go` 的独立快照和成员账本约束订阅份额，关联原有订单、Key 和请求记录。

上游窗口百分比不等于绝对 Token 或美元余额。官方 Codex 协议包含 `used_percent`、`window_duration_mins`、`resets_at`，展示层还可能四舍五入。模型、上下文、推理、工具和缓存都会影响订阅消耗。因此不能承诺每笔请求都能从两次百分比快照精确算出消耗。

参考：[官方额度协议](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/account.rs)、[官方用量说明](https://learn.chatgpt.com/docs/pricing)。官方说明同时列出 Plus 与 Pro 的用量限制，不能仅凭 Pro 名称认定无限。


## 本轮实现范围与操作方式

后台发布商品时可选：

| 模式 | 放行依据 | 固定 `$` 字段 |
| --- | --- | --- |
| 动态观察 `dynamic_shadow`（新商品默认） | 继续使用原有 `$` 限额，同时采集动态账本 | 仍须配置，作为观察期间的实际限制 |
| 动态额度 `dynamic` | 真实上游窗口、个人累计份额、原子预占与并发限制 | 必须为 0，避免叠加隐藏的固定限额 |
| 原 Token / `$` 模式 | 保持已有规则 | 保持购买时配置 |

修改商品仅影响后续新订单。已付款订单不会自动切换模式。动态观察订单也不会自行转为正式动态订单；完成观察后，管理员为新商品选择正式动态模式。

正式动态发货要求：账号来自独立拼单号池、普通 OpenAI OAuth 账号、有效且新鲜的额度窗口、非上游封顶状态。发货与初始权益、专属 Key、通知处于同一事务，无有效基线时整体不发货。首个窗口按交付时真实剩余量扣除 2 个百分点安全余量后均分。

目前接入普通 Codex 主订阅窗口，Plus、Pro 都以实际返回的窗口为准。没有任何可靠窗口时视为未知；没有实现“无窗口即无限”的分支。独立 Spark 账号及 `codex-spark` 请求暂不支持正式动态模式，避免把不同模型可用量混用。

实现参数：

- 后台每 30 秒扫描拼单 OAuth 账号，每批最多 4 个并行探测；数据库租约合并多实例刷新，每账号 30 秒内至多取得一次租约。探测超时 25 秒，失败不发布虚构快照。
- 快照新鲜度为 2 分钟；超时暂停正式动态请求，已有在途请求可继续结算。上游明确拒绝时暂停，不将拒绝伪造为用户消耗了 100%。
- 每个窗口独立保留整号 2 个百分点。冷启动预估暂用每 `$1` 对应 10 个百分点、单请求至少预占 1 个百分点，并限制整号同时只有 1 个在途请求。
- 有可归属的真实增量后，按账号和窗口学习“百分点 / Standard `$`”比例，后续预占增加 25% 余量；支持小数消耗。这个学习比例会在同账号的新周期和新订单中沿用，不是承诺美元与订阅容量等价。
- 请求的 Standard `$` 结算后仍显示“估算”；只有已归属的上游增量完成校准，才显示“已校准”。没有最终用量的请求保持待核对，并保留对应容量占用。

校准批次保留所有未校准请求，不因某次探测百分比没变化而删除样本。上游新增消耗先进入待归属余额；批次仍有在途、账单不确定或晚于探测时刻完成的请求时，等待后续快照。批次可确认后，将累计增量按实际 Standard 成本权重分配给成员。没有本地待归属请求的新增消耗才记为外部消耗。配额判断同时检查成员总权益与实际上游剩余，并继续扣除未覆盖的本地估算。

第一版采用账号、窗口级学习，尚未按模型、推理强度和缓存分别建立学习参数；高频并发持续没有静止采样区间时，也可能长时间保持保守估算。上游取整、延迟和平台外使用仍会影响归属精度，“已校准”表示已按批次规则核对，不代表上游提供了逐请求的精确账单。生产启用前应先观察真实测试账号，不能直接将统计比例视为精确硬上限。

用户在拼单卡片查看各窗口的整号剩余、本人消耗、预占、个人剩余和同步时间。在原“使用记录”的拼单筛选下查看最近 100 条动态明细，支持 Key 筛选；该明细明确独立于原账单日期筛选。所有用量查询都以登录用户身份限定，不接受查询参数替换用户身份。

数据库新增迁移 `244_pool_dynamic_quota.sql`，保留既有订单合法数据，增加快照、窗口、成员权益、请求校准状态和刷新租约表。没有修改旧迁移、普通 sub2 号池归属或钱包扣费方式。回退应用前，应先停止发布新的动态商品并妥善处理动态订单；旧应用不能正确执行新的动态额度规则，不能直接回退后继续服务动态订单。

## 公平分配规则

每个实际额度窗口独立建立权益账本，单位为“该窗口满额的百分点”。两人团均分每个窗口的可分配容量，三人团三等分；人数取订单席位数，不取当前在线人数。

发货时必须获取可靠基线。若账号某窗口仅余 80%，首个窗口就以这 80% 减安全余量后均分，不能将发货前消耗记给新成员；商品应说明首个窗口按交付时实际余额分配。上游确认重置后才建立新窗口。

不能每次刷新都把当前剩余量重新平分。例如忽略安全余量，100% 的两人团中 A 已用 30 个百分点、B 未用，账号剩 70%，应保留 A 可用 20、B 可用 50，而不是各重新分到 35。

正常消耗扣减调用者的份额，其他人的份额保留。只有确认上游容量变化、外部消耗或人工更换账号等事件时才重算总容量；重算仍考虑每人已用及预占，优先保证累计使用较少成员的剩余权益。已经消耗的额度不能撤回，超出重新校准后份额的成员停止新请求，不继续借用他人的额度。

容量调整可采用均衡累计使用的分配算法：设各成员当前窗口已用加预占为 L_i，账号经过校对、扣除未覆盖消耗及安全余量后尚可新分配的容量为 R，求共同水位 T，使所有 max(T-L_i,0) 之和等于 R；这些差值即各成员可新增使用量。每个窗口分别计算，不能混加 5 小时和周的百分点。

## 消耗估算与校准

1. 请求前以实际模型、输入输出上限、缓存情况、服务档位等估算窗口消耗，原子预占成员份额与账号容量。所有适用窗口均通过才能放行。
2. 请求后记录可靠 Token 用量及现有 Standard `$` 用量账单。另行记录该请求的窗口消耗估算值，不修改已经结算的 `$` 历史账单。
3. 使用响应头及主动探测的上游快照校对账号总消耗。只有能确认时间覆盖范围的快照才能校准对应请求批次。
4. 同一采样区间存在并发调用时，将增量按该批次请求的估算权重分摊并记录置信状态，不能全部扣给最后完成的人。估算权重可先使用 Standard 成本，再由真实样本按模型、档位、缓存等校准；不能假定官方 API 价格与订阅消耗永远成固定比例。
5. 百分比暂时不变，不表示请求免费。保留累计估算和待核对状态，待后续可测增量一起校准。没有足够样本时降低账号总并发、限制大请求，并采用保守预占；单请求独占采样区间也不能消除上游延迟与取整误差。
6. 发现未能归属平台请求的额外消耗，记录为账号外部消耗或待核对差额，缩减可用容量并提示管理员，不伪造某成员使用记录。

Standard `$` 只作为统一账单和初始估算特征。实际订阅份额校准要考虑 Fast 等影响上游消耗的条件，即使现有商品约定的 Standard 账单不加该倍率。额外付费 credits 不自动并入订阅容量，也不自动购买或使用重置。

## Plus、Pro 与探测异常

| 账号状态 | 处理方式 |
| --- | --- |
| Plus 返回有效 5 小时与周窗口 | 两个窗口分别均分和预占，任一不足即等待 |
| Pro 没有某个窗口 | 不人为创建该窗口限制 |
| Pro 实际返回有限窗口 | 遵守真实窗口，不因为名称是 Pro 跳过 |
| 明确无限的资源 | 不虚构总量，按成员并发与公平调度共享服务能力 |
| 缺少字段、探测失败或过期 | 显示未知或同步中，不能当作 0% 已用或无限 |

短时探测失败可沿用最近可靠快照并扣减本地新增消耗与预占，但不能增加容量。超过配置的新鲜度期限则暂停新请求或使用预先明确的保守兜底规则；不能自动退到更宽松的固定预算。初次无基线的账号不进入动态发货。

重置不能仅依据本地时钟推演就清空权益。需要有效新快照确认周期切换；乱序旧快照和小幅时间漂移不能触发重复重置。在途调用保留预占，待确认属于哪个窗口后迁移或结算，不得丢弃，也不得永久重复扣两次。

## 实现结构

- 新增独立动态配额模式，旧已付款订单维持购买时的约定，不自动替换权益。
- 保存账号每个上游资源桶与窗口的快照、采样时间、来源、窗口代次、版本和置信状态；不能仅依赖 `accounts.extra` 的最后值。
- 建立成员窗口账本和不可变的预占、结算、校准事件，关联原 `pool_requests` 与使用记录。
- 沿用现有数据库事务锁顺序，统一账号、订单和成员的放行判断，跨进程共享预占；每次快照和结算均有幂等标识。
- 快照有明确覆盖边界，已包含在上游剩余额度里的消耗不能再次扣减。尚未覆盖的完成请求和在途预占必须保留，避免并发超发。
- 主动探测由服务端任务执行，响应头作为补充，不依赖管理员打开账号页面。对同账号合并刷新、限频退避；轮询间隔根据实测延迟和接口限制确定。
- 同账号存在不同模型资源桶时分别约束对应请求，不把互不替代的容量合并。

## 用户展示

保留“相当于 1/2 Plus”“相当于 1/3 Pro”，增加“动态均分”标识。每个窗口展示账号剩余、个人剩余、在途预占、上次同步时间和重置时间；个人百分比明确是“占本人份额”还是“占整号”，不能混用。

使用记录继续放在现有页面，保留 `$` 费用，增加订阅份额消耗及“估算 / 已校准 / 待核对”状态。解释 `$` 为标准 API 用量参考，实际能否继续请求以动态订阅份额为准。校准记录可追溯，余额变化有原因。

## 验收与上线顺序

先以影子模式采集真实专属测试账号：只计算、不改变现有限额，观察上游延迟、百分比精度、模型差异和外部消耗。数据足够后，限定新测试商品启用动态约束，再推广至新正式商品。

必须验证先用者不能重复分配、离线成员份额保留、不同模型与并发批次归属、探测丢失和乱序、重置与在途跨窗口、校准幂等、未知 Pro 窗口、不同资源桶，以及账单不重复扣钱包。估算导致的单次超额无法完全排除：保留实际消耗并停止该成员继续调用，不能承诺百分比探测能提供精确硬上限。

## 本轮验证结果

- 真实 PostgreSQL 集成测试：全部 `TestPool*` 通过，包括旧 Token / `$` 订单、商品购买、发货、退款、Key 隔离及新增动态模式。
- 校准专项覆盖：预估 1pp 实际 20pp 全额归属本人、其他成员权益保留、零增量后迟到更新、在途期间测量暂存、实际成本批次权重、幂等结算、外部消耗、跨重置预占迁移、乱序快照和提前重置拒绝。
- 接口与服务回归通过：原 OpenAI 额度查询、字段缺失/真实零值解析、刷新租约、最大 4 并发、停止取消、使用记录的登录身份隔离、动态请求使用 Standard 估算及 Spark 模式边界。
- 前端拼单相关测试、类型检查、语言键完整性与生产构建通过；小额 `0.0025 pp` 不会显示成 0。
- 包含前端资源的服务端构建通过。本地独立预览服务已升级，已有演示数据迁移成功；管理员和成员的订单、动态记录及商品管理接口冒烟验证通过。

这些是本地自动化验证，测试账号及上游快照均为合成数据；没有用客户 OAuth 凭据发送真实消费请求，也没有把新规则发布到生产。正式推广前仍需按前述观察流程验证真实账号的探测延迟与模型消耗差异。
